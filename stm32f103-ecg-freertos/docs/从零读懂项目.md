# 从零读懂：STM32F103三导联模拟采集与FreeRTOS

这份文档对应 `ecg_f103_freertos` 工程。目标是让你能沿着代码解释一次采集、一次任务切换和一次丢包恢复，而不只是运行程序。函数名均来自当前源码，可在编辑器中直接搜索。

建议边读边打开源码。第一次先读第1～5节，理解数据流；第二次读第6～10节，理解并发和通信；最后做第12节实验，准备第13节的问答。

## 1. 先说清楚：这个项目究竟做了什么

因为作者只有STM32最小系统板，没有心电模拟前端和RC滤波器。因此，本工程先由单片机产生三路PWM模拟信号，通过跳线送回真实ADC，采集后用FreeRTOS组织处理，再经串口发给电脑。电脑显示波形，并在丢包后请求补传。

```text
板内波形表 → TIM4三路PWM → PB6/PB7/PB8
                               │ 三根跳线
                               ↓
                          PA0/PA1/PA4
                               ↓
TIM3定时触发 → ADC1依次扫描三个通道 → DMA双半缓冲
                               ↓ 中断通知
                         高优先级采集任务
                     三路平均 → 1600组历史缓存
                               ↓
                        通信任务组织数据包
                               ↓ USART2 + TX DMA
                       CH340 → 电脑C语言上位机
                               ↓
                   校验、去重、发现缺口、请求补传
```

**“三导联”描述模拟信号的含义，“三通道ADC扫描”描述硬件采集方式。** 本版没有人体电极输入，也没有三套同时采样的ADC。ADC1依次转换IN0、IN1、IN4，三个结果之间存在时间差。

项目有价值的部分是这条完整链路的时序、资源分配和错误处理。它是嵌入式采集与可靠传输实验，不能表述为已经完成医用心电仪。

## 3. 上电以后，程序按什么顺序运行

从 `startup.S` 进入 `main()` 前，会完成C运行所需的初始化，包括复制有初值的数据、清零BSS。业务入口在 `firmware/app.c`。

`main()` 的顺序是：

1. `board_init()` 设置时钟、引脚、串口、PWM、ADC和DMA，但暂不启动采集触发。
2. `xTaskCreateStatic()` 创建采集、通信、监测三个任务，保存任务句柄。
3. `vTaskStartScheduler()` 启动FreeRTOS调度器。
4. 采集任务优先级最高，首先执行，在任务内调用 `board_start_sampling()`。
5. 采集任务随即等待DMA通知，让出CPU，通信和监测任务得以运行。

为什么不能在任务句柄建立前就启动ADC？因为DMA中断会用 `adc_handle` 通知采集任务，目标必须已经存在；把启动放在调度器开始运行后，也避免了尚未进入正常任务环境就发生采集通知。

这里没有一个包办所有事情的主循环。每个任务内部各有一个循环，但会通过等待通知或延时进入阻塞状态。

## 4. 没有ADS1293和RC，三路信号怎么产生

### 4.1 波形表保存的是PWM占空比

`waveform.h` 包含200组比较值。`board_set_wave(index)` 将一组值写入TIM4的CCR1、CCR2、CCR3，对应PB6、PB7、PB8。

三根跳线是：

| PWM输出 | ADC输入 | ADC规则序列位置 |
|---|---|---:|
| PB6 / TIM4_CH1 | PA0 / IN0 | 1 |
| PB7 / TIM4_CH2 | PA1 / IN1 | 2 |
| PB8 / TIM4_CH3 | PA4 / IN4 | 3 |

PA2和PA3继续用于USART2，不参与ADC扫描。PWM比较值以约128作为中心，I和II模拟PQRST形态，III在去掉中心偏置后满足II−I的构造关系。三个波形不是三个独立自由变量。

TIM4的计数周期为256个72MHz时钟，因此PWM频率为：

```text
72,000,000 / 256 = 281,250 Hz
占空比约为 CCR / 256
```

200个波形点按250点/秒更新，一轮为0.8秒，对应约75次/分钟。

### 4.2 ADC看到的是脉冲，平均后才有波形

没有RC时，ADC脚上主要是0V与约3.3V切换的PWM，而不是平滑的心电电压。占空比越大，一段时间内读到高电平的比例通常越高。把每通道256次结果平均，可以估计占空比对应的平均码值。

理想直觉是“平均ADC码≈4095×占空比”，但实际会受边沿、输入建立时间和采样相位影响。12位ADC输出不等于本系统拥有12位有效精度，数字平均也不能等同于完整的模拟抗混叠滤波。

TIM3的1125时钟周期与PWM的256时钟周期互质，有助于避免始终采到相同的名义PWM相位；ADC实际采样还受自身时钟同步约束，因此不能仅凭互质就保证波形精度。

## 5. ADC、DMA和平均怎样配合

### 5.1 必须区分三种“采样率”

| 名称 | 当前值 | 含义 |
|---|---:|---|
| ADC扫描触发率 | 64,000次/秒 | 每次触发顺序转换三个通道 |
| ADC转换总量 | 192,000个结果/秒 | 64,000×3，三个通道合计 |
| 最终记录率 | 250组/秒 | 每通道256次结果平均成一个点，一组含三点 |

TIM3时钟72MHz，PSC=0、ARR=1124，因此触发周期是1125个时钟，约15.625µs。ADC时钟12MHz，每通道采样7.5周期、转换12.5周期，三路总时间约为：

```text
3 × (7.5 + 12.5) / 12 MHz = 5 µs
```

5µs小于15.625µs，当前配置给一次扫描留下了时间余量。三个通道依次转换，不能把它说成严格同时采样。

### 5.2 DMA内存的排列

一次扫描按IN0、IN1、IN4的顺序写入，内存像这样：

```text
第0次扫描：I0, II0, III0
第1次扫描：I1, II1, III1
……
第255次扫描：I255, II255, III255
```

`adc_average()` 用 `input[i * 3 + channel]` 按通道累加。累加器是32位，因为4095×256会超过16位范围；`(sum + 128) / 256` 是整数四舍五入。

### 5.3 一个循环缓冲分成两个半区

每半区包含256次扫描×3通道×2字节=1536字节，两个半区合计3072字节。

```text
时间：       0～4ms       4～8ms       8～12ms
DMA写入：     半区0        半区1         半区0
任务可处理：   等待         半区0         半区1
```

DMA到半满产生HT中断，到全满产生TC中断，循环重新开始。半区填满时间是256/64000=4ms，所以平均后每4ms得到一组三通道记录，即250组/秒。

DMA不会等任务。采集任务必须在该半区再次被写入前读完。`board_adc_valid()` 检查DMA剩余计数、待处理中断标志、当前代数和故障状态，判断这半区是否还能读。

`acquisition_task()` 在平均前后各检查一次，同时要求通知数恰为1、代数连续。若发现堆积、覆盖或漏采，就调用 `board_stop_sampling()` 并挂起采集任务。这样界面能看到故障，而不是继续输出看似连续的错误数据。

注意：停采后串口补传不能重新创造漏掉的ADC结果。补传只解决“已经采到、仍在历史缓存里，但电脑没收到”的数据。

## 6. FreeRTOS为什么这样分任务和优先级

### 6.1 三个任务的截止时间不同

| 任务函数 | 优先级 | 何时运行 | 为什么这样安排 |
|---|---:|---|---|
| `acquisition_task` | 4 | DMA通知后 | 半区约4ms后可能被覆盖，需要及时处理 |
| `communication_task` | 2 | 每次循环后阻塞1ms | 串口要持续服务，但短暂让位不会立即破坏ADC数据 |
| `monitor_task` | 1 | 500ms周期 | 心跳和统计容许更大延迟 |
| FreeRTOS Idle | 0 | 其他任务都阻塞时 | 内核空闲任务 |

高优先级不等于一直占用CPU。采集任务用 `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` 阻塞等待，只有数据就绪时才参与调度。若把这个等待改成无限忙等，低优先级通信任务可能无法运行。

DMA中断经 `app_adc_interrupt()` 调用：

```c
BaseType_t wake = pdFALSE;
vTaskNotifyGiveFromISR(adc_handle, &wake);
portYIELD_FROM_ISR(wake);
```

第一句通知目标任务，第二句在有必要时请求切换到刚唤醒的高优先级任务。中断只交接信息，耗时平均留给任务完成。直接通知适合这里“一个中断通知一个固定任务”的情况，不必为768个采样值额外建队列再复制一遍。

通知本身不保护DMA内存，所以仍需要代数和半区有效性检查。

### 6.2 任务优先级和中断优先级，方向相反

| 比较对象 | 数字越大意味着什么 |
|---|---|
| FreeRTOS任务优先级 | 更优先，例如采集4高于通信2 |
| NVIC中断优先级 | 更不紧急，例如UART的4比ADC DMA的5更紧急 |

`FreeRTOSConfig.h` 设置了4个中断优先级位，调用内核API的阈值为 `5 << 4`。

本工程UART RX的NVIC优先级为4，因此可以在普通FreeRTOS临界区中响应，但**不能调用FreeRTOS API，包括FromISR版本**。ADC DMA优先级为5，允许调用FromISR通知；TX DMA优先级为6；SysTick/PendSV为15。

这里提高UART RX紧迫度，是为了及时把到来的字节搬进接收环形缓冲。UART中断很短，不在中断中解析完整协议，也不做打印或等待。

### 6.3 两种延时的区别

通信任务的 `vTaskDelay(1ms)` 从调用时刻起阻塞，真实循环周期还包括本轮工作时间，所以不是精确的1kHz定时任务。

监测任务的 `vTaskDelayUntil(..., 500ms)` 按上一次计划唤醒时间推进周期，减少工作耗时造成的长期漂移。ADC采样时序则由硬件TIM3决定，不能靠任务延时产生。

### 6.4 静态任务和任务栈

三个任务使用 `xTaskCreateStatic()`，栈和任务控制块TCB都是全局静态对象，没有运行时申请堆内存。好处是内存开销可在链接时核算。

本移植中一个栈字为4字节。采集256字=1024字节、通信448字=1792字节、监测160字=640字节。`uxTaskGetStackHighWaterMark()` 返回历史上最小剩余栈空间，不是“当前空闲RAM”，也不是CPU利用率。

`configCHECK_FOR_STACK_OVERFLOW=2` 与溢出钩子提供检查，但不能取代合理的栈预算和压力测试。

## 7. 多任务共享数据，为什么没有到处加互斥锁

设计首先限制“谁能写”，再给必要的共享访问加保护。

| 对象 | 写入者 | 读取者 | 协作方式 |
|---|---|---|---|
| ADC双半缓冲 | DMA硬件 | 采集任务 | 完成通知、代数和DMA位置校验 |
| 历史缓存 | 采集任务 | 通信任务 | 通信每次复制一组时进入短临界区 |
| UART RX字节环 | UART中断写head | 通信任务读并推进tail | 单生产者/单消费者与发布顺序 |
| 发送缓冲 | 通信任务 | UART TX DMA | busy为0才组包和启动下一次发送 |
| 诊断计数 | 采集/通信/监测各自更新对应项 | 通信任务打包 | volatile字段；整包不是同一瞬间的原子快照 |

`send_samples()` 没有把25组的整个复制过程包进一个长临界区，而是每组只保护一次 `history_get()`。这会暂时阻止采集任务切入写历史，避免复制到半新半旧的一组。优先级4的UART RX仍然可以响应。

UART环形缓冲数组有256字节，head/tail用8位变量自然回绕，预留一个空槽区分满与空，因此实际最多存255字节。ISR先写字节，再发布head；任务先取字节，再推进tail。

`volatile` 告诉编译器按要求访问共享对象，不能自动让多步操作成为原子操作，也不能代替锁。这里能工作依赖于单核、中断优先级、所有权和短临界区的组合。

TX DMA发送是异步的。如果发送尚未完成就重写发送缓冲，线上数据会被破坏。当前只有通信任务组包，且先检查 `board_uart_busy()`，发送缓冲一直保留到DMA完成。

## 8. 历史缓存和串口数据包怎么设计

### 8.1 序号和环形位置不是同一个东西

每组记录有一个递增序号；数组位置是 `sequence % 1600`。`history.next` 表示下一组将分配的序号，有效范围为 `[oldest, next)`。

例如next=2000时，最旧序号oldest=400，缓存保存400～1999。序号400和2000会落在相同槽位，但它们属于不同时间的数据。读取必须先判断有效范围，再做取模。

`history_get()` 的三个返回值值得记住：

| 返回值 | 意义 | 通信如何处理 |
|---:|---|---|
| 1 | 还在缓存，已复制到输出 | 加入DATA包 |
| 0 | 尚未产生 | 不把未来数据当作有效样本 |
| -1 | 已被覆盖 | 返回GAP，说明无法补回 |

记录大小为3×2=6字节，1600组占9600字节。保留时间1600/250=6.4秒。这是RAM历史，掉电后清空。

### 8.2 串口只有字节流，没有自动的数据包边界

发送一次不意味着电脑一次就读到完整一包。一次ReadFile可能得到半包，也可能包含多个包。因此协议必须有帧头、长度和校验。

| 字段 | 字节数 | 目的 |
|---|---:|---|
| A5 5A | 2 | 找帧起点 |
| version | 1 | 当前版本1 |
| type | 1 | 区分数据、状态和命令 |
| session | 4 | 区分不同连接会话 |
| sequence | 4 | 首条记录序号或消息相关序号 |
| count | 2 | 本包包含/请求的组数 |
| size | 2 | 负载字节数 |
| payload | 0～150 | 记录或状态内容 |
| CRC16 | 2 | 检查传输损坏 |

多字节整数显式按小端写入，不直接发送C结构体，避免结构体填充和布局差异。CRC覆盖version到payload末尾，算法为CRC16-CCITT-FALSE，初值FFFF、多项式1021。

CRC只能帮助判断内容是否损坏；序号才用来识别“少了哪组”。CRC也不是加密或身份认证。

`parser_push()` 逐字节积累，先检查帧头和字段形状，再等完整长度，最后核验CRC。候选帧不合法时丢掉一个字节继续找头，逐步重新同步。包长有限，畸形长度不会让程序无限申请内存。

### 8.3 包类型与发送顺序

| 包 | 方向 | 含义 |
|---|---|---|
| DATA | 板→PC | 最多25组三通道记录 |
| STATUS | 板→PC | 采样率、通道数、缓存边界、错误数 |
| DIAG | 板→PC | 运行次数、耗时、栈余量、实际任务优先级 |
| GAP | 板→PC | 指定历史已过期 |
| BIND | PC→板 | 建立本次会话 |
| HELLO | PC→板 | 请求状态 |
| READ | PC→板 | 请求从某序号开始的1～25组记录 |

通信任务每次先检查TX是否空闲。当前实际顺序是：待发/定期STATUS → 待发DIAG → 实时数据 → 补传。所谓“实时优先”是指实时数据优先于补传，并不是高于所有控制包。

通常积累25组发一次实时包，间隔约100ms。一包为18+25×6=168字节，10包/秒约1680字节/秒。115200的8N1每字节占10个线位，理想单向上限为11520字节/秒；扣除状态、诊断和调度开销后，仍有补传空间，但不能直接把理论余量当成实测吞吐。

## 9. 丢掉5秒，具体怎样补回来

### 9.1 电脑先确定记录起点

电脑通过BIND建立会话，以首个匹配STATUS的next作为本次记录起点。连接前没有接收过的历史不算本次丢包。后续包需要匹配session，避免混入旧连接的数据。

### 9.2 用一个例子串起整个恢复过程

假设已经收到0～999，之后电脑主动丢弃5秒接收数据，板子仍正常采集，1000～2249共1250组没有进入电脑接收器。

1. 电脑继续读取串口但丢弃字节，这避免了“只是把数据积压在电脑串口缓存里”的假断传。
2. 5秒后恢复解析，收到新的DATA或STATUS，接收器知道当前序号已经前进。
3. `receiver_request()` 从最早缺口开始找，生成READ，例如从1000开始请求25组。
4. 板上 `handle_command()` 保存请求；通信空闲且没有更高顺序待发包时，从历史缓存取数据返回。
5. 电脑将补传放回对应序号位置；当前请求范围收齐后，尽快请求下一段。
6. 100ms仍有请求范围内的数据未到，则重发请求；重复返回的数据会被去重。
7. 如果所需数据已经被覆盖，板子返回GAP，电脑将其计入过期，而不是继续无限重试。

这里是按缺口请求的选择性补传，没有每包都等待ACK的停等实时发送机制。

### 9.3 电脑端三个关键字段

`receiver.c` 的 `floor` 是当前窗口起点，`next` 是已知数据末端的后一位，`samples` 最多保存2000组。每个槽位同时保存序号和valid，不能只凭数组位置判断数据存在。

`receiver_get()` 检查范围、valid和序号匹配；已存在的序号再次到达只增加重复计数。`advance_floor()` 推进窗口时计算真正没有收到的记录数量，累加expired。

因此，**missing=0不一定代表全部恢复成功**：历史过期后，缺口已经移出窗口，也可能显示missing=0。必须同时看expired和应收/实收数量。

### 9.4 为什么6.4秒缓存只能说“实测支持5秒”

断传恢复时，最早丢失的数据已经变老，恢复后的请求等待和传输还会继续消耗余量。5秒断传只有约1.4秒的初始缓存余量，最旧缺口必须尽快补回；补传过程中还要继续采集与发送新数据。

所以缓存容量、实际恢复延迟、有效补传吞吐和连续重试共同决定能否恢复。超过缓存范围、板子复位或掉电都不能保证补齐。本工程验证的是保持供电并主动丢弃接收字节，不是断电恢复实验。
